# UI Patterns
- Prefers debounced search inputs (~300ms delay) rather than filtering on every keystroke. Confidence: 0.85
- Designs UI components to accept custom/external data lists (via props or store) rather than being tightly coupled to internal API calls, so they can be reused in different contexts (e.g., global search). Confidence: 0.75
- Search bar visibility should be controlled by a store flag — hidden by default (via opacity/pointer-events), toggled on only when a search-relevant page mounts (e.g., Home, SelectDevice), and toggled off on unmount. Prevents UI setup issues from components that mount before search infrastructure is ready. Confidence: 0.80
- When displaying a list of cards/items in a confined sidebar section, paginate with a small fixed number per page (e.g., 2) and provide `< >` navigation controls with a page counter for overflow, rather than scrolling through a long list. Confidence: 0.70
- Avoid using `navigate(-1)` for back-button navigation in multi-tab contexts — it creates navigation loops. Instead, track the origin via a store flag and navigate to an explicit route (e.g., `/selectDevice`). Confidence: 0.75
- Separate the "clear search query" action from "close/navigate away" — clear should only reset query text without any navigation side effects. Confidence: 0.70
- When a close/exit button is pressed on a search-triggered page, **navigate home first, then let route-change effects clear search state** — don't clear search before navigating. This avoids races where debounced navigation effects see stale query text and navigate back. The exit action should be instant; cleanup should be reactive (triggered by leaving the route), not imperative in the click handler. Confidence: 0.80
- Prefers fine-grained, honest task statuses — when a multi-phase task enters an intermediate wait queue (e.g., waiting for a transfer slot), show a distinct status label (e.g., `queueTransfer`) rather than leaving it stuck at the previous phase's status (e.g., 99% "downloading"). Users should always see what a task is actually waiting on. Confidence: 0.85
- In Electron apps with a custom titlebar, elements inside the main content area must use `h-full` (relative to the parent flex container) rather than viewport-relative heights like `h-screen`, `min-h-screen`, `100vh`, or `100dvh`. The parent container already accounts for the titlebar height via `flex: 1`, so viewport units cause overflow past the titlebar. Confidence: 0.80
- In Electron apps, avoid relying solely on `onContextMenu` (right-click) for important UI interactions like toggling collapsible content — the platform may intercept or block context menu events on certain elements (e.g., `<button>`). Instead, provide an explicit, visible toggle control (e.g., a small chevron icon button) as the primary interaction, using `e.stopPropagation()` to prevent parent click handlers from firing. Confidence: 0.75
- Prefers modal dialogs (full-screen overlay with backdrop blur) for quick secondary actions or confirmations — rather than cramming them into inline sections. However, for substantial, information-rich content like changelogs, release notes, or update progress, prefers a dedicated page/route in the Content area (alongside home, download, settings) that the user navigates to, rather than a modal dialog. The page pattern gives the content full real estate and feels like a first-class destination. Confidence: 0.75
- Prefers explicit, clearly-labeled action buttons (e.g., "Khởi động lại ngay") for primary CTAs rather than making an entire card/container clickable for the primary action. Implicit click targets reduce discoverability; users expect to see a button for the thing they want to do. Confidence: 0.80

- Pages in the Electron app should use `fixed` positioning with CSS custom property offsets (`top: var(--titlebar-height)`, `left: var(--sidebar-w, 0px)`) to sit within the content area, rather than covering the titlebar/sidebar or using viewport-relative positioning that ignores chrome dimensions. This pattern is used across Settings, Downloads, and other main pages. Confidence: 0.80

- Prefers `motion/react` (the Motion library for React) for UI animations — including `AnimatePresence` for mount/unmount transitions, `whileHover`/`whileTap` for micro-interactions, and animated layout properties. The user considers poor or missing animations a quality issue ("hiệu ứng không đẹp"). Confidence: 0.75
- When `AnimatePresence` wraps a list rendered with `.map()` (multiple children rendered simultaneously), use `mode="popLayout"`. Never use `mode="wait"` with multiple children — `wait` expects a single exiting child and a single entering child, and will produce visual glitches (and a console warning) when multiple items animate in/out at once. Confidence: 0.70

- When creating new pages, match the visual style and structure of existing pages (header layout, spacing, font sizes, border separators). The user values page-to-page visual coherence — inconsistency is perceived as sloppy. Confidence: 0.70

- When adding a new page that should coexist with the visible sidebar (i.e., a sidebar-route page), use the `flex flex-col size-full` layout pattern from `home.tsx` rather than `fixed` positioning with CSS custom property offsets. The `home.tsx` pattern naturally sits inside the flex layout alongside the sidebar, so the sidebar stays visible without manual offset calculation. The user explicitly considers `home.tsx` the reference standard for sidebar-route page layout. Confidence: 0.75

- In Electron custom titlebars, `no-drag` (`-webkit-app-region: no-drag`) should be applied **conditionally** based on element visibility, not unconditionally. When an interactive element (button, input) is hidden (e.g., via `opacity-0 pointer-events-none`), the `no-drag` class must be removed so the hidden element's geometry doesn't block the drag region. Only visible/interactive elements should override the drag region. Confidence: 0.80

- When multiple settings rows relate to the same feature (e.g., control style + control position both being about window controls), prefer consolidating them under a single `Section` rather than splitting across multiple `Section` components. This reduces visual fragmentation and signals to the user that the settings are a coherent group. Confidence: 0.65
